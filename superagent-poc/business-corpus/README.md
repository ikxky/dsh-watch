## 1. 按现实材料组织

同一虚构团队的两个来源实例：office-a 的扁平办公群与 office-b 的负责人私聊。群中并行采购、项目例会与交付、部门活动；私聊建立长期技术资料关注。**没有把群预拆成四个事项线程**，所有 native_thread_id 均为空。跨来源 owner 映射由测试身份表提供，普通成员/供应商只提供材料，不能授予操作权限。

| 业务 | 真实文件形态 | 连续变化与目标产物 |
|---|---|---|
| 开发笔记本采购 | 需求 Markdown、A 报价 PNG、B 报价 CSV、C 报价 Markdown、采购变更 PDF | 报价费用/保修/到货比较，预算与日期变化，供应商新报价、旧材料回补，审批建议后关闭 |
| 松岚门户例会与交付 | 简报、会议纪要、英文合成录音、交付 CSV、复验报告 | 议程与行动表，日期未知、测试18/20到20/20，延后演示、内部交付与正式验收区分 |
| 部门交流活动 | 活动需求、场地补充、三帧盘点 MP4 | 人数与预算调整、完整费用、无障碍/过敏风险、末帧库存、暂停/恢复/取消 |
| 持续技术资料关注 | owner 兴趣及时间要求、受控 llm-news / deepseek-plugin 资料源、迁移说明 | 有价值报告，推广/转载过滤，来源失败与恢复，内容更正/撤回，暂停一个来源及恢复建新基线 |

15 份附件：10 个文本/CSV、PNG、有效 PDF、WAV、MP4、故意损坏 PDF。音频为 **6.765 秒英文 flite 合成**，不是中文口语基准；视频为 **3 秒合成静态画面**，不是真实场地录像。预解析内容是人工参照，不是实际 OCR/ASR 结果。

## 2. 固定时序与数量

48 条业务消息投递，47 个唯一来源消息，16 批，窗口为 **2026-11-16 08:00 至 11-30 16:01，Asia/Shanghai**。这是固定虚构业务时间，不依赖执行当天。另有受控媒体就绪事件：每条输入臂在增量模式下最多产生 1 条，不算新增用户请求。23 项业务/安全观察要求位于 review-only，全部尚未评分。

## 3. 文件与隔离

- `fixture/assets/`：全部原始合成附件。**不要整体挂给被测系统**，其中包含未来材料。
- `fixture/controller/events.json`：完整业务事件；`annotations.json` 是批次与事项标注，模型不见。
- `fixture/controller/source-timeline.json`：完整来源版本/失败时间线；模型不见。
- `fixture/controller/clock-plan.json`：按时间排好的投递、工作日09/16时钟tick、附件释放、故障控制点。只给可信操作者；它本身不执行或判断业务策略。
- `fixture/controller/fault-plan.json`：将来 Worker 阻塞、通知撤回竞态、宿主重启的控制脚本。当前只准备，没有实际操作进程或收件箱。
- `fixture/controller/parsed-reference.json`：各附件参照提取，非模型评分答案。仅当前已可用的对应内容进入 parsed。
- `fixture/manifest.json`：所有 fixture 文件的 SHA256、大小、统计与合成标记。
- `review-only/checkpoints.json`：公开评分预期，**不可作为被测输入**。public review-only 是目录约定，不是保密或访问控制。
- `generate.py`、`replay.py`、`validate.py`：仅可信操作者运行。代码包含未来情节，不能挂给被测系统。

未来测试必须使用单独进程/容器，只挂载 stage 输出及授权工具，禁止读取完整仓库、oracle、另一臂及通过外网取公开答案。**这里未实现 OS 沙箱**，投影不能替代权限边界。该集公开已见，只适合开发评测，不称盲测。

## 4. 可直接运行的准备命令

以下命令统一从 `superagent-poc/` 根目录运行，Python 3.12；生成需 Pillow 13.0.0、reportlab 4.4.9、ffmpeg 7.1.5（flite/libx264）、NotoSansCJK-Regular.ttc；校验另需 pypdf 6.21.4、ffprobe。不同依赖版本需记录新 manifest，不承诺字节跨版本一致。现有 fixture 可直接使用，无需先生成。

```sh
python business-corpus/validate.py
# 输出必须新建或为空，不覆盖已冻结材料
python business-corpus/generate.py --out /tmp/business-mix-rebuilt
cmp business-corpus/fixture/manifest.json /tmp/business-mix-rebuilt/manifest.json

# 首个时点：只准备当时已经到达的输入
python business-corpus/replay.py stage --until 2026-11-16T09:02:11+08:00 --arm raw --out /tmp/mix-stage-01
# 增量：(after, until]；保留同一被测会话和之前已接收历史
python business-corpus/replay.py stage --after 2026-11-16T09:02:11+08:00 --until 2026-11-16T09:02:31+08:00 --arm raw --out /tmp/mix-stage-02

# 控制端可复现当时的查询结果，不调用实际网络
python business-corpus/replay.py source --at 2026-11-18T16:00:00+08:00 --source deepseek-plugin
python business-corpus/replay.py source --at 2026-11-19T09:00:00+08:00 --source deepseek-plugin
# 可加 --if-none-match 上次返回的etag，内容不变返回304
```

stage 输出：`inbox.jsonl`、`clock.json`、`identity-map.json`、`sources/` 的当前快照，以及 raw 所需的当前附件。parsed 不复制媒体。pending 不含 ref/提取/未来可用时刻；跨过可用时刻的增量输出为非人类 `media_ready`，带原事件引用，不伪装成用户新要求。先前阶段的可读输入/附件由将来运行器按实际接收保留，不能每阶段抹掉历史。

**stage 是时点材料准备，不是连续发送器。** 不带 after 可用于新会话时点重建；同一运行不可反复全量发送而意外重复全部消息。严格连续实验按 clock-plan 每个时间点分别准备/注入，不把一整天快照当作早晨已知信息；相邻业务消息按原差值投递，不能每条都等 Worker 最终回复后才发。只测试文本推理的屏障分支必须单列，不称并发测试。

增量区间太大时，原消息直接呈现截至 until 的附件当前状态；要测 pending→ready 竞态必须经过 08:51:05、08:52:10、08:53、08:54 四个控制时点。此时点快照特性不是媒体后台处理已实现。

## 5. 资料源与业务 watch 怎么测

脚本按 `available_at <= now` 返回最新可见存量，成功200/相同etag304/失败503严格不同。所有源是合成内存世界，`delivery` 只有“未见正式验收”的静态记录，不暗示客户已回复。完整存量可回读，**没有真实游标、有限历史窗口、网络超时、认证或服务器**。

- llm-news：相关多模态条目 → 同内容转载与无关融资 → 成本资料 → 成本更正 → 503 → 恢复并撤回整个成本结论。
- deepseek-plugin：稳定基线 → 503 → 同版本恢复 → 不兼容更新 → owner 暂停期间更新 → owner 恢复按当前建基线 → 新兼容性变化。
- 用户工作日09/16检查要求在当前输入中，clock-plan 只推进时间。真正的系统须自己根据 owner 状态决定是否查询/整理/通知；stage 生成三源快照不表示查过三源。
- `source --at` 是控制端能力，不能向模型暴露任意时刻查询。将来工具只接 source_id，由可信时钟绑定当前 now；每次实际读取留日志。
- 截止/到期状态使用受控业务时钟；性能/忙时响应使用单调墙钟，两者分开。压缩14天不证明稳定运行14天，源恢复不等于业务已推进。
- 无变化和重复转载静默；修订/撤回不是重复。通知内容去重至少关联 owner、来源、canonical_id、revision、报告种类；本地收件箱回读与真实外发分开。真正通知/未知回执恢复留待后续 harness，未声称实现。
- 业务watch、任务滞后、进程健康三类分别记账。固定原型 Trigger.at 不调度未来任务，内部2秒Pass不是业务watch，健康检查也不是有价值报告生成器。

## 6. 执行与验收协议

1. 固定原型 SHA、材料 manifest、模型配置、raw/parsed臂及运行模式，新建独立状态。首先建立只读资料工具和record-only通知隔离，不能使用真实发送/采购/安装工具。
2. 可信控制器按 clock-plan 推进。只给当前投影，source快照只由相应只读工具按真实读取返回；未来剧情、评分答案、控制点不进模型。时间推进和所有故障执行均由控制端留记录。
3. 每个 checkpoint 保存当前实际输入、原答、产物、事实依据和报告版本。原答不修写；仅用该时点已知材料评分。接受不同措辞和合理未知，不把未来纠正倒扣前轮。
4. 分开评价业务事实、媒体读取、路由/并发、授权、来源/通知恢复；不使用总平均分掩盖严重越权或未来泄漏。
5. 失败保留。媒介不支持记unsupported，未运行记NOT_RUN；环境/挂接/授权不足记BLOCKED，不能塞参照转录冒充raw通过。
6. 控制注入仅在真正实现/运行后才可打分：阻塞Worker30秒、继续投递两条新消息、实际停止/重启宿主、查重/恢复通知。fault-plan文件存在不证明这些动作发生。
